# 云端协同架构开发技能 (Cloud-Edge Collaborative Development)

## 触发时机与适用场景

当需求涉及以下场景时触发本技能：
- 连接自建私有服务器、Node.js/Python 后端或云端 BFF 网关；
- 实时 PTT 语音录入直传、流式 TTS 播放或网络音频流式交互；
- 接收大模型（LLM）结构化数据渲染智能卡片（单词卡、汉字卡、看板 HUD、智能工牌）；
- 虚拟视口长文本分页、1-bit/2-bit 压缩点阵动画推流或被动 NFC 云端中继联动。

设备定位为**物理终端与交互视口**（传感器、屏幕视口、按键、双向音频），外部服务端负责**复杂计算、大模型调用与业务状态存储**。完整通信规范请参阅 [`docs/cloud-edge/architecture.zh_CN.md`](../../docs/cloud-edge/architecture.zh_CN.md)。

## 硬件与资源不可逾越红线 (ESP32-C3)

1. **内存预算上限**：
   - ESP32-C3 可用堆内存仅约 100 KB，且**无 PSRAM**。
   - 单个网络接收缓冲区最大设为 4 KB。
   - 严禁将完整 JSON、长文本或未经压缩的原始图像全量载入堆内存。

2. **零 Flash 音频直通流与按键映射**：
   - **硬件按键映射**：板载仅有 `UP`、`DOWN`、`OK` 三个物理按键（共用 GPIO0 ADC 电阻分压梯，无独立语音侧键）。PTT 语音直传通常映射为**按住 `OK` 键**（按下触发 `ptt_start`，松开触发 `ptt_end`），`UP`/`DOWN` 键复用为视口滚动与菜单导航。
   - **音频录入（PTT 16kHz 16-bit PCM，约 32 KB/s）**：必须通过 2 KB 双缓冲从 I2S 麦克风直接泵送至 WebSocket 发送队列。
   - **音频播放（流式 MP3/PCM）**：从网络接收后写入环形缓冲区，喂给轻量软件解码器（如 Helix-MP3），解码为 PCM 后送入 I2S DMA 播放。
   - **绝对红线**：严禁将音频流分片写入板载 NOR Flash（SPI 总线竞争会导致音频破音卡死，且加速 Flash 寿命损耗）。

3. **长文本虚拟视口滑动窗口（统一走 WebSocket 分页）**：
   - 对于电子书、长篇新闻或大模型长回复，设备端绝不缓存全文。
   - 设备仅向服务端按需请求**当前可视视口窗口**（当前屏 + 预加载一屏，RAM 占用恒定 < 1 KB）。
   - **翻页交互**：按 `UP`/`DOWN` 翻页时，必须通过当前保持的 WebSocket 文本帧发送 `{"type":"page_req", ...}`，**严禁使用 REST 请求翻页**，彻底杜绝连续翻页引发的 TLS 重复握手与延迟。
   - 服务端负责根据屏幕点阵（240×320）计算折行、字数和分页索引（`page_idx`, `total_pages`）。

4. **复古调色板单色/双色视频引擎**：
   - 禁止在片上尝试原画 MP4/H.264 解码（240×320 原始真彩单帧需 150 KB，直接打爆内存）。
   - 动画与视频流必须由服务端转码为 1-bit / 2-bit RLE 压缩位图（Pip-Boy 辐射绿、琥珀黄、黑客帝国黑绿、Game Boy 灰阶等调色板）。
   - 设备端仅负责解压缩位图并推送到 ST7789 屏幕，支持零开销 CRT 隔行扫描线效果。

5. **NFC 动态云端中继**：
   - 板载 NTAG213 为被动标签，容量固定不可变。
   - 勿将其作为动态存储介质；仅使用其固化的 UID 或静态 URL 作为索引键，通过服务端完成动态业务映射与重定向。

6. **强制 WebSocket 交互铁律 (Mandatory WebSocket Invariant)**：
   - **交互式 AI 问答、语音对讲、卡片状态同步与流式音视频，必须强制使用单一全双工 WebSocket (WSS) 长连接**。
   - **严禁将 REST API 用于语音对讲或交互式 AI 循环**。根本原因：
     1. **无 PSRAM，RAM 存不下录音**：5 秒 PCM 录音需 160 KB，而 ESP32-C3 可用堆仅 ~100 KB，根本无法在内存中缓冲整段录音后再 POST，必须通过 WSS 边采边推（2 KB 双缓冲直通）。
     2. **TLS 握手内存突增 (RAM Spike)**：每次 HTTPS 握手瞬时消耗 30~35 KB 堆内存，频繁短连接极易引发堆碎片化与 OOM 崩溃；WebSocket 仅开机/唤醒时握手一次，进入传输态常驻仅需 ~12~16 KB。
     3. **全双工流式与即时打断**：REST 半双工无法并发下发 UI 卡片与音频流，更无法实现中途打断。
   - **连接生命周期与省电规范**：
     - 会话活跃期复用 WSS 连接，由事件或心跳保活。
     - 若连续无交互超时（推荐 30~60 秒），客户端主动关闭 WSS 连接并让 Wi-Fi 芯片进入 Modem-Sleep 省电；用户按下按键瞬间唤醒重连（支持 TLS 会话复用以实现亚秒级重连）。
   - **内嵌多语言字库与生字位图旁路**：
     - 设备端如需显示中、日、英 UI 文本，直接调用独立的 [`passport-cjk-font`](../passport-cjk-font/SKILL.zh_CN.md) 技能集成预编译的 837 KB CJK 二进制字库（`noto_cjk_16_compact_4bpp.bin`，通过 `esp_partition_mmap` 零内存开销映射）。
     - 当遇到极端罕见冷僻字、笔顺分解动画或本地字库未收录符号时，服务端通过 WSS 文本或二进制帧直接下发 1-bit 单色位图/点阵（如 64×64 位图仅 512 字节），彻底绕开单片机 Flash 字库容量限制。

## 双通道通信架构

- **REST API (HTTP/HTTPS) —— 严格限定于离线/冷路径**：
  - 仅用于一次性、低频或无状态配置：设备注册激活、Wi-Fi 配网凭据校验、静态资源版本拉取。
  - 单次响应必须精炼（JSON < 512 字节）。
  - **严禁**用于语音上传、实时问答、大模型 Token 吐字流或卡片状态同步。
- **WebSocket (WSS) —— 交互式 AI 与流式多媒体的唯一标准**：
  - 承载所有热路径交互：PTT 语音直传、LLM 打字机流式推送、卡片结构化数据下发、TTS 音频下发、富媒体/点阵位图推送与按键遥测。
  - 帧复用标准：
    - 文本帧：控制信令、状态同步、卡片结构化 JSON（`type: "cmd"`, `"card_word"`, `"card_char"`, `"page"` 等）。
    - 二进制帧：带标识前缀的纯数据（`[0x01]` 实时音频流、`[0x02]` 点阵/位图帧）。

## AI 协作实施流程

1. **分清职责边界**：
   - 设备端代码位于 `main/`（UI 布局、按键事件、WSS 客户端任务）。
   - BSP 硬件驱动位于 `components/bsp/`。
   - 业务逻辑、大模型调度、数据库和媒体转码属于独立后端。
2. **多任务解耦**：
   - 网络和音频任务独立于 LVGL GUI 任务运行。
   - 网络回调更新界面元素时，必须持有 `bsp_lvgl_lock()`。
3. **验证与交付**：
   - 运行 `./tools/validate.sh --static` 验证代码规范与主机测试。
   - 运行 `./tools/validate.sh --firmware` 验证固件编译与镜像封装。
